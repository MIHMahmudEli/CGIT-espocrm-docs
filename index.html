EspoCRM Feature Guide

Seventeen improvements made to this EspoCRM instance, explained in plain language with a picture of each screen.

EspoCRM 10.0.8 17 features Updated 19 October 2026

What’s new

Everything below was added without changing the EspoCRM program itself, so a future upgrade will not lose any of it. Feature 1 is the foundation the others are built on.

1The Product Service catalogue

A brand-new record type — Product Services — now sits in EspoCRM beside Calls. It is simply the list of everything you sell, and it is what ties a lead to the calls made about it.

FieldWhat it holds
NameThe product or service in your own words — required
CategorySoftware, Hardware, Service, Consulting or Other — required, defaults to Software
TypeProduct, Service, Package or Subscription — required, defaults to Product
PriceIn Taka (৳) — the one currency this system uses — required
StatusActive, Inactive or Discontinued — required, defaults to Active
DescriptionFree text for anything worth noting
Assigned To / TeamsWho looks after this product, and which teams see it
Created / ModifiedRecorded automatically
  • Two products exist today: X — ৳20,000.00 and Y — ৳30,000.00, both Active.
  • A product service is required on every lead and every call — that single rule is what powers features 5, 6 and 8.
  • Leads can be searched by phone number and filtered by product service — see section 2.
  • Leads and calls belonging to a product are listed on the product’s own page.
For developersHow feature 1 is built

A record type built from metadata alone — EspoCRM creates the table, the menu tab, the list and the detail view from JSON, so no core file is involved.

Files touched
  • custom/Espo/Custom/Resources/metadata/scopes/CProductService.json — turns the entity on: entity: true, ACL, menu tab
  • custom/Espo/Custom/Resources/metadata/entityDefs/CProductService.json — fields, links and indexes — category, type, status, price
  • custom/Espo/Custom/Controllers/CProductService.php — API controller, extends the core record controller
  • custom/Espo/Custom/Resources/metadata/clientDefs/CProductService.json — page icon and the Calls / Leads panels
  • custom/Espo/Custom/Resources/layouts/CProductService/list.json — list columns
  • custom/Espo/Custom/Resources/i18n/en_US/CProductService.json — labels and option names, mirrored across 37 locales
How it works
  • The scope carries isCustom: true and module: "Custom", so an upgrade leaves it alone.
  • Leads and Calls each hold a required linkMultiple field cProductServices, through the relations cLeadProductService and cCallProductService.
  • price is a currency field and is what the Lead form sums up in feature 3.
If you change it
  • A new field needs an entityDefs entry and a cache clear, or the table column is never created.
  • Labels live in Resources/i18n/<locale>/CProductService.json — add the key to every locale file or the field shows its API name.

2Searching and filtering the lead list

Three changes make the Leads list quicker to work with: you can type a phone number into the search box and get the right person, you can find a lead by part of its website, and you can cut the list down to the leads belonging to one product service.

Where the list search looksExample that works
Name (first and last)jihad
Account nameDelta
Email addresssales@
Address — street and cityDhaka
Phone number new01716099707, 017 or 1820154087
Website newcgitapps, example.com or https://zz-website
  • Part of a number is enough — the search looks inside the number, so 017, 16099707 and a full number all find the same lead.
  • Part of a website is enough — the search looks inside the link, so cgitapps, example.com and a full web address all find the same lead.
  • The search box in the application’s top bar finds leads by number as well.
  • You can also filter by status, assigned user, team, date, industry and the rest — the product filter simply sits at the top of the list.
  • More than one product can be chosen at a time, and several filters can be used together.
  • Everything is cleared with the × button next to the search box.
  • Meetings and emails are not affected — this applies to the Leads list only.
For developersHow feature 2 is built

Three metadata files: one widens what the list search looks at, one teaches it to match inside a website, and one puts the product filter first.

Files touched
  • custom/Espo/Custom/Resources/metadata/entityDefs/Lead.json — collection.textFilterFields and collection.fullTextSearch
  • custom/Espo/Custom/Resources/metadata/selectDefs/Lead.json — textFilterUseContainsAttributeList — the website matches anywhere in the text
  • custom/Espo/Custom/Resources/layouts/Lead/filters.json — order of the filter panel
How it works
  • textFilterFields adds first name, last name, street, city, phone and website on top of the core three; each one becomes a LIKE clause built by Espo\Core\Select\Text\DefaultFilter.
  • A plain LIKE only matches from the start of the value, so cgit would never find https://cgitapps.com. textFilterUseContainsAttributeList turns a field into a contains match — the same hook feature 14 uses for the call product name.
  • The website is a url-type field, so it stays off the fulltext index and is reached by the LIKE path alone; from four characters up, any fragment of the link finds the lead.
  • For a phone field the server only runs the match when the input is digits, spaces or + ( ) -, so typing abc never matches a phone number.
  • fullTextSearch: true also switches global search to relevance order.
If you change it
  • A field must exist in entityDefs first — an unknown name in textFilterFields is skipped silently.
  • filters.json only sets the order; the widget each filter uses comes from core field metadata.

3The opportunity amount fills itself in

While you are creating a lead, choosing its product service also works out the Opportunity Amount on the same form from that product’s price. Choose two products and the two prices are added together.

What you doWhat happens to Opportunity Amount
choose one product servicethat product’s price is put in — ৳20,000.00 for product X
choose a second product servicethe two prices are added together — ৳20,000.00 + ৳30,000.00 = ৳50,000.00
take every product back outthe field is emptied
type a figure of your own and leave the products aloneyour figure stays exactly as you typed it
type a figure of your own, then change the products againyour figure is replaced by the new total
pick a product that has no price yetit adds nothing — the rest still count
  • Works both on the full lead form and on the smaller quick-create window.
  • The amount sits in the Details panel, just below Status and Source.
  • Amounts are always whole Taka — a price with a fraction is rounded.
  • Nothing is saved until you press Save, so the figure can still be corrected by hand.
  • The price used is the product’s price at that moment. If you change a product’s price later, leads already saved keep the amount they were given.
For developersHow feature 3 is built

Client-side only: the Lead form watches the product list, fetches the prices it has not seen yet and writes the total.

Files touched
  • client/custom/src/views/lead/record/edit.js — sums the product prices into Opportunity Amount
  • client/custom/src/views/lead/record/edit-small.js — the same logic inside quick-create
  • custom/Espo/Custom/Resources/layouts/Lead/detail.json — where the amount is displayed
How it works
  • metadata/clientDefs/Lead.json registers both views under recordViews.edit and recordViews.editSmall.
  • The view listens to change:cProductServicesIds and reacts only to changes made in the UI (options.ui), so a load does not rewrite the field.
  • Prices come from GET /CProductService?select=id,price, are cached in productPriceMap, summed and rounded; an empty product list clears the amount.
If you change it
  • productPriceMap lives as long as the page does, so a price edited in another tab is only picked up after a reload.
  • The calculation never runs server side — the saved value is whatever the form held when Save was pressed.

4Desktop notifications

A bell in the top bar lets you switch on alerts that reach your computer directly — a call reminder, for example, will still arrive with the browser closed.

  • Notifications are only ever switched on by you clicking the bell — no pop-ups appear on their own.
  • You can mute individual categories from your preferences.
  • The same bell shows at a glance whether notifications are on, off or blocked.
  • The banner carries your own logo rather than the EspoCRM one.
  • Needs HTTPS (or localhost) and the scheduled job to be running.
Brave says “Notifications were not enabled”? Brave blocks web push by default, so the bell turns on and then quietly fails. Open brave://settings/privacy, switch on Use Google services for push messaging, close Brave completely and start it again, then click the bell once more. The restart is required — the switch does nothing until Brave is reopened. Chrome, Edge and Firefox need no extra step.
For developersHow feature 4 is built

Web Push, end to end: a navbar toggle, a service worker, a subscription record and a scheduled job that does the sending.

Files touched
  • client/custom/src/views/site/navbar/web-push.js — the bell; asks for permission only when you switch it on
  • client/custom/src/helpers/web-push-manager.js — registers sw.js and calls the subscription API
  • public/sw.js — receives the push and shows the system notification
  • custom/Espo/Custom/Controllers/PushSubscription.php — action/vapidPublicKey | status | subscribe | unsubscribe
  • custom/Espo/Custom/Notification/NotificationService.php — notifyUser() sends mail and push from one place
  • custom/Espo/Custom/WebPush/*.php — VAPID keys, payload encryption and the HTTP sender
  • client/custom/img/cgit-logo-192.png — the logo drawn on the system notification (192×192)
How it works
  • metadata/app/clientNavbar.json adds the item and points it at custom:views/site/navbar/web-push (template custom:site/navbar/web-push).
  • The subscription is a PushSubscription row with acl: false; muting is stored per user in the Preferences field webPushMutedCategories.
  • A scheduled job (metadata/app/scheduledJobs.json, every minute) is what actually pushes — nothing is pushed from the page request itself.
  • Full setup, tests and the production notes are in custom/Docs/WebPush.md.
If you change it
  • A new category needs PushPreferences::CATEGORIES, a Preferences field in entityDefs, and a bump of SW_VERSION in public/sw.js or old workers keep the old list.
  • The toast icon comes from ICON at the top of public/sw.js: give a replacement a new file name (the OS caches an icon against its URL) and bump SW_VERSION.
  • Push only works over HTTPS. The VAPID keys sit in data/webpush-config.php, which is not in git.

5Smarter history

A record’s History panel used to list every activity in the company. It now shows only the activity belonging to that record’s own product service (the catalogue from section 1), so you see the relevant calls and nothing else.

  • The filter switches on automatically — nothing to click.
  • A record with no product service still shows its full history.
  • The list refreshes as soon as you save the record.
For developersHow feature 5 is built

The history panel keeps all of its behaviour and gains one filter: the parent record’s product services.

Files touched
  • client/custom/src/views/record/panels/history.js — sends productServiceIds and refreshes after a save
  • custom/Espo/Custom/Resources/metadata/app/clientRecord.json — swaps the panel view for every record type
  • custom/Espo/Custom/Tools/Activities/Api/Get.php — reads the query parameter
  • custom/Espo/Custom/Tools/Activities/Service.php — narrows the query to the product’s calls
  • custom/Espo/Custom/Resources/routes.json — overrides the core Activities routes
How it works
  • Custom routes win because Espo\Core\Utils\Route::unify() loads custom definitions first and skips duplicates, so /Activities/:parentType/:id/:type runs the custom controller.
  • The view copies cProductServicesIds into collection.data.productServiceIds; Service::getActivitiesQuery() restricts Calls to that list and returns an empty id list for every other type.
  • The panel refetches 150 ms after after:save, so a call just made appears without a reload.
If you change it
  • Turn the filter off by not sending productServiceIds — the API treats it as absent and returns everything.
  • A record with no product service set is not filtered, so it still shows the full history.

6Every call shows its product service

A call now carries the product it is about, exactly as a lead does. It gets its own column in the Calls list, so you can see at a glance which product a call belongs to without opening anything — and it is required, so no call is ever filed against nothing at all.

For developersHow feature 6 is built

A required link field plus two layouts — the column and the panel are metadata, not code.

Files touched
  • custom/Espo/Custom/Resources/metadata/entityDefs/Call.json — cProductServices, linkMultiple, required
  • custom/Espo/Custom/Resources/layouts/Call/list.json — the Product Services column, width 16, after Parent
  • custom/Espo/Custom/Resources/metadata/clientDefs/Call.json — relationship panel on the detail view
  • custom/Espo/Custom/Resources/i18n/en_US/Call.json — the column label
How it works
  • The link is hasMany through relation cCallProductService, declared on both ends so the two records stay in step.
  • Nothing visible was added in JavaScript — the column and the panel are read straight from layout JSON.
If you change it
  • Removing required: true reopens the option of saving a call with no product.
  • Layout edits need Admin → Clear Cache before the list rereads layouts/Call/list.json.

7Call date and time fill themselves in

Two fields — Call Date and Call Time — now sit on every call form, and both arrive already filled in: today’s date, and the time right now. A small grey line under each one spells out what those boxes mean — Today, Today 03:57 PM — so nothing has to be decoded before the call can be saved.

AboutWhat happens
Call Datea date field, defaulted to the day you open the form
Call Timea date-and-time field, defaulted to the moment you open the form
Both fieldsrequired — a call cannot be saved without them
The time pickeroffers half-hour steps, while the default is the exact minute you opened the form
In the formthey read 02/10/2026 and 03:57 PM, the local format from section 10
The grey lineunder each field spells the value out as Today, Tomorrow or Yesterday — and moves the moment you pick another day
Any other datethe Call Date line stays silent, since the box already reads that date; the Call Time line shows the full date and time
On the saved recordthey read Today and Today 03:57 PM
After savingthey never move on their own — correct them by hand if the call was logged at another time
  • Both fields sit just below Date Start, Date End, Duration and Product Services — in the full form and the small pop-up alike.
  • Because they arrive filled in, saving a call needs only two things: pick the lead and write the note.
  • The grey line is only there to be read — the real date and time stay in the boxes, and that is what gets saved.
  • They describe when the call was logged; Date Start and Date End still describe when it happens.
  • The values are stored, so the figure you read is the figure that was true at the time.
For developersHow feature 7 is built

The defaults are still pure metadata; the relative wording is two tiny field views that only touch the form.

Files touched
  • custom/Espo/Custom/Resources/metadata/entityDefs/Call.json — the two fields, their defaults and their views
  • client/custom/src/views/fields/call-date.js — the grey line under Call Date
  • client/custom/src/views/fields/call-time.js — the grey line under Call Time
  • custom/Espo/Custom/Resources/layouts/Call/detail.json — where they sit on the detail view
  • custom/Espo/Custom/Resources/layouts/Call/detailSmall.json — and in the side panel
  • custom/Espo/Custom/Resources/i18n/en_US/Call.json — "Call Date" and "Call Time"
How it works
  • cCallDate is a required date with default: "javascript: return this.dateTime.getToday();".
  • cCallTime is a required datetime with default: "javascript: return this.dateTime.getNow(1);" and minuteStep: 30.
  • The javascript: prefix is evaluated by core against the model, so the value follows the user’s own time zone rather than the server’s.
  • Both fields carry a client-side view key, which is how core picks a field’s class per entity; the two views extend views/fields/date and views/fields/datetime untouched.
  • The views append one span.call-date-hint under the field in edit mode only, and re-render it on change:<field>; the detail view keeps the wording core already writes.
  • The line reads Today, Tomorrow or Yesterday, comparing the stored day against moment.tz(...).startOf('day') in the user’s zone — the same range test core uses on the detail view.
If you change it
  • Neither field carries duplicateIgnore, so a duplicate (feature 9) copies them along with everything else.
  • Metadata edits require a cache clear before the defaults change.
  • Plain client/custom/src files load on demand and need no build step, but a cache clear still refreshes the metadata that points at them.

8Calls fill themselves in

When you set a call’s parent to a lead, the form completes itself: the name comes from the lead and the product service — from the catalogue in section 1 — is chosen for you. If that lead covers several products, you are asked which one applies. The same happens on a meeting: set its parent to a lead and the products arrive there too.

If the lead…Then
has no product servicenothing happens — the field is left for you
has exactly one product serviceit is filled in straight away, no questions asked
has two or more product servicesa selection box opens so you can choose
you tick nothing in the boxnothing is applied and the field stays as it was
you already filled the field yourselfyour choice is never overwritten
you change your mind and pick a different leadthe previous answer is replaced with the new lead’s products
  • Meetings behave the same — parent a lead and the products fill themselves in, picker included, even in the small calendar form.
  • Product Services is required on a meeting too, so a multi-product lead left unanswered blocks Save there just as it does on a call.

The Call form watches the Parent field, reads the lead, then either fills the product in or asks you which one applies — and the Meeting form watches the same way.

Files touched

  • client/custom/src/views/call/record/edit-small.js — the same, inside quick-create
  • client/custom/src/views/meeting/record/edit.js — the same watchers, on the Meeting form
  • custom/Espo/Custom/Resources/metadata/clientDefs/Call.json — registers both views
  • client/custom/src/views/modals/select-product-service.js — the product picker
  • client/custom/res/templates/modals/select-product-service.tpl — its checkbox list
How it works
  • The view reacts only to UI changes (options.ui) and requests GET /Lead/<id>?select=id,name,cProductServicesIds,cProductServicesNames.
  • One product is written straight into cProductServicesIds/Names; several open the modal and wait for its select event.
  • The call name is filled only while it is empty, so it never overwrites something you typed.
  • The Meeting edit view carries these exact watchers and the same modal; opening a meeting whose products are already set leaves them alone.
If you change it
  • cProductServices is required, and the modal starts with nothing selected — a multi-product lead left unanswered blocks Save.
  • The modal is custom too: it is created as custom:views/modals/select-product-service.
  • Meeting’s cProductServices was marked required in entityDefs/Meeting.json when the prefill arrived, so both activity forms validate alike.

9Duplicate calls start with a clean description

Open the … menu on any call and choose Duplicate. A brand-new call form opens with everything carried over from the original — the parent, the dates, the duration, the product service and the attendees — except the Description, which arrives empty. Nothing stops you duplicating; you simply have to write what the new call was about before it can be saved.

On the duplicated formWhat happens
Name and Parentcarried over from the original call
Date Start, Date End and Durationcarried over
Call Date and Call Timecarried over
Product Services, attendees, assigned usercarried over
Descriptionemptied — you must type it before the call can be saved
The “reminder already sent” markcleared, so the new call is treated as its own record
The old history notenot copied — the new record starts its own
  • Duplicating is never blocked — the empty description is the only thing between you and Save.
  • Because Description is required, no duplicate can ever be filed with a blank note.
  • The original call is left exactly as it was; nothing on it is edited or removed.
  • Status is not carried over either — the new call starts at Planned, its default.
For developersHow feature 9 is built

One field flag. Core’s duplicator drops anything marked duplicateIgnore, so the copy arrives with an empty description.

Files touched
  • custom/Espo/Custom/Resources/metadata/entityDefs/Call.json — description set to required + duplicateIgnore
  • application/Espo/Core/Record/Duplicator/EntityDuplicator.php — core code that honours the flag — read-only reference
  • custom/Espo/Custom/Hooks/Call/DescriptionDiff.php — records what is typed afterwards
  • custom/Espo/Custom/Hooks/Meeting/DescriptionDiff.php — the same hook for meetings
How it works
  • Duplicate on the detail view posts to Call/action/getDuplicateAttributes, then creates with options.duplicateSourceId.
  • Espo\Core\Record\Service::getDuplicateAttributes() runs the duplicator, which unsets every duplicateIgnore field.
  • status is never copied by core, so a duplicate starts at its default (Planned).
  • DescriptionDiff reads the X-Duplicate-Source-Id header so it knows the copy has no baseline text.
If you change it
  • Delete duplicateIgnore from entityDefs/Call.json and duplicates behave exactly as they did before.
  • Fields added later are copied by default — mark them duplicateIgnore if they should not be.

10Dates and times in local format

The whole application now uses the 12-hour clock and day-first dates, set to Dhaka time. Nothing needed reprogramming — it was a setting.

  • While you are typing, dates read 02/10/2026 and times read 02:30 PM.
  • Lists and record pages keep the friendly reading — Today, Yesterday, 02 Oct, Today 03:57 PM — exactly as before.
  • Time zone is Asia/Dhaka (UTC+6) throughout.
  • Stored records are untouched — only the display changed, so no data was migrated.
  • The date separator changed from a full stop to a slash; it can be put back in one line if preferred.
For developersHow feature 10 is built

There is no feature code here at all: three values in one config file do the whole job.

Files touched
  • data/config.php — timeZone, dateFormat, timeFormat and weekStart
How it works
  • The file holds timeZone: Asia/Dhaka, dateFormat: DD/MM/YYYY, timeFormat: hh:mm A and weekStart: 0.
  • PHP reads them through Espo\Core\Utils\Config; the browser receives them from the config API and formats every date it draws.
  • Timestamps are still stored in UTC — only the display changes.
  • Nothing under custom/ or client/custom/ mentions these keys.
If you change it
  • Admin → Settings writes the same values, so data/config.php is a starting point rather than a lock.
  • Change the format in one place and the calendar, lists and forms all follow (the calendar week runs Sunday to Saturday because of weekStart).

11Meetings start faster

Creating a meeting used to need two bits of typing before you could save. Now the meeting name fills itself in from whoever the meeting is about, and you are already listed in the attendance panel.

  • Switching the parent updates the name automatically.
  • Typing your own name first is respected — it will not be replaced.
  • Attendance is only pre-filled on a new meeting; existing meetings are never altered.
  • Smaller pop-up forms behave the same way.
For developersHow feature 11 is built

Two client views: one copies the parent’s name into the meeting name, the other puts you on the invite.

Files touched
  • client/custom/src/views/meeting/record/edit.js — name autofill, attendee prefill and the feature 8 product watchers
  • client/custom/src/views/meeting/record/edit-small.js — extends the edit view for quick-create
  • custom/Espo/Custom/Resources/metadata/clientDefs/Meeting.json — registers recordViews.edit and editSmall
How it works
  • fetchParentName() runs on change:parentId change:parentType, requests <parentType>/<id>?select=id,name, and writes name only while it is empty or still holds a value this view wrote itself.
  • fillAttendees() runs only for a new meeting with no attendees and sets usersIds / usersNames / usersColumns to the logged-in user.
If you change it
  • The name step is skipped for parent types with no name field in entityDefs.
  • Typing a name by hand stops the autofill for good — the view remembers what it wrote in autoFilledName.

12New records start with you as their owner

Opening any of the five create forms — a product, an account, a call, a meeting or a lead — used to leave Assigned User empty, so a new record arrived with nobody on it and it was easy to forget who was meant to look after it. They now arrive already set to you — whoever happens to be signed in.

What you doWho the record belongs to
open any of the five create formsyou — set before the form even opens
open a record that already existsunchanged — only new records are affected
pick somebody else, then savethe person you picked — the starting value is only a suggestion
leave it alone and press Saveyou
sign in as somebody else and create a recordthat person — it is always whoever is signed in
use the smaller pop-up form insteadyou — it behaves exactly the same way
  • One less field to fill in on every record you create.
  • The five are product, account, call, meeting and lead — every other entity keeps core’s behaviour.
  • It is only a starting point — nothing is saved until you press Save.
  • The record goes on showing you as its owner until somebody changes it.
  • Records brought in by import, by another integration or by a workflow are not touched.
  • Existing records are never re-assigned — the rule applies only while a record is being created.
For developersHow feature 12 is built

One model-default preparator, wired into five scopes: core asks it for values just before a new form opens.

Files touched
  • client/custom/src/handlers/defaults-preparator.js — returns assignedUserId and assignedUserName
  • custom/Espo/Custom/Resources/metadata/clientDefs/{Account,Call,CProductService,Lead,Meeting}.json — the key modelDefaultsPreparator in each
How it works
  • Core helpers/model/defaults-populator calls prepare(model) for a new model only, then applies the result silently; anything supplied in the URL is applied afterwards and wins.
  • The handler returns {} when the record already has an owner, or when the entity has no assignedUser field.
  • Account got a clientDefs file of its own for the wiring; the other four already had one.
  • The handler began life under handlers/lead/ and was moved up one level when the other four scopes joined.
  • Teams are not touched.
If you change it
  • prepare() must never throw — the create form awaits it.
  • Adding a sixth entity is one line in its clientDefs — the same handler serves them all.

The Week view is where the day is actually spent, and it did not look like the rest of the calendar: today was not marked in any way, each day was headed by a single line of Mon 05, and an entry showed nothing but its time and its title. Week now follows the Month view’s language, so the two screens read the same.

Month and Timelinenot part of this change — no weekday-and-date headings, no chips
  • Today is unmistakable at a glance, in both Week and Day.
  • The two chips answer “what is this and where is it up to” without opening the record.
  • Times are aligned down the gutter and across the entries, so a busy day is easy to scan.
  • Only the rendering changed — the same events, colours, filters, drag-and-drop, week navigation and refresh are all exactly as they were.

For developersHow feature 13 is built

A custom calendar view layered over the core CRM calendar: the same events, rendered the way Month already renders them.

Files touched
  • client/custom/src/views/calendar/calendar.js — titleFormat, dayHeaderContent, eventContent, eventClassNames
  • client/custom/res/templates/calendar/calendar.tpl — the toolbar: prev / next / Today, the date title, the mode buttons
  • client/custom/css/calendar-week.css — the Month-matched styling
  • custom/Espo/Custom/Resources/metadata/clientDefs/Calendar.json — registers the view, the template and the stylesheet
How it works
  • Fields on an Dep.extend class are shadowed by class fields, so template, titleFormat and events are assigned inside setup() rather than at class level.
  • dayHeaderContent builds the weekday and date whenever arg.view.type.indexOf('timeGrid') === 0 — that is Week and Day; Month returns arg.text untouched.
  • eventContent adds the type and status chips when hasEventMeta() (all-day, or at least MIN_META_DURATION = 45 minutes) plus the attendee rows beneath.
  • The title uses titleFormat.week = 'D MMM YYYY' joined by core’s rangeSeparator ( – ).
If you change it
  • Custom CSS is appended to cssList, so calendar-week.css loads after espo.css — that is why plain :root overrides such as --fc-today-bg-color win.
  • FullCalendar is told about every change through setOption from an instance-accessor setter, which runs before render(), so there is no flash of the old style.
  • The toolbar is a custom: template — adding a button means editing calendar.tpl, never the core file.

14Find a call by its product

The search box on the Calls list no longer looks at the call name alone. Type the name of a product service and the calls about that product come back too — no need to open each call to see what it was about.

  • A call about two products is still one row — searching never shows the same call twice.
  • Sorting keeps working while a search is on, whatever column the list is ordered by.
  • Filters, primary filters and the count above the list behave exactly as they did.
  • A product name matches anywhere in the text from four characters up; a shorter search still matches from the start of the name.

For developersHow feature 14 is built

Two metadata entries and one small class — the search box is given one more field to match, and the join behind it is de-duplicated.

Files touched
  • custom/Espo/Custom/Resources/metadata/entityDefs/Call.json — collection.textFilterFields gains cProductServices.name
  • custom/Espo/Custom/Resources/metadata/selectDefs/Call.json — matches anywhere in the text, and picks the filter class
  • custom/Espo/Custom/Classes/Select/Call/TextFilter.php — adds DISTINCT for the many-to-many join
How it works
  • List search reads entityDefs.Call.collection.textFilterFields; a dotted entry such as cProductServices.name is left-joined and searched alongside name — the same shape core already uses for CampaignLogRecord.
  • Both sides of the product link are hasMany, so the ORM makes it many-to-many through a middle table and one call joins one row per product. Core DefaultFilter adds DISTINCT only for hasMany, which would list a two-product call twice.
  • selectDefs.Call.textFilterClassName therefore points at a subclass of DefaultFilter that calls distinct() whenever a joined attribute is in the filter, so no core file is touched.
  • selectDefs.Call.textFilterUseContainsAttributeList makes the product name match anywhere in the text from four characters up; the call name keeps core behaviour.
If you change it
  • Metadata only — clear the cache after any edit to entityDefs/Call.json or selectDefs/Call.json.
  • Deleting the cProductServices field leaves the dotted entry behind: remove collection.textFilterFields and the selectDefs entries at the same time, or the search errors out.
  • Drop textFilterUseContainsAttributeList and the product name matches from the start only, like the call name.
  • The class is needed only while the relation is many-to-many; if the product link ever becomes a plain belongsTo, delete it along with the textFilterClassName line.

Nothing has to be set up.

AboutWhat happens
Who is remindedthe meeting’s Assigned User

Statusonly while the meeting is still Planned — Held or Not Held meetings are left alone

  • Meeting reminders travel the same road as call reminders — pop-up, panel and push — and are labelled separately, so one can be muted without the other.
For developersHow feature 15 is built

The twin of the Call Route reminder: a scheduled job scans for meetings whose Date Start has arrived and hands each one to the shared NotificationService.

Files touched
  • custom/Espo/Custom/Jobs/MeetingReminders.php — the scheduled job
  • custom/Espo/Custom/Resources/metadata/app/scheduledJobs.json — registers it to run every minute
  • custom/Espo/Custom/Resources/metadata/entityDefs/Meeting.json — the marker field that remembers what was already notified
  • custom/Espo/Custom/Resources/i18n/en_US/Meeting.json — the message and push wording
  • custom/Espo/Custom/Resources/i18n/en_US/ScheduledJob.json — the job label in Admin → Scheduled Jobs
How it works
  • The job reads scopes.Meeting.activityStatusList (Planned) and asks for every meeting whose dateStart is at or before now but inside the last reminderPastHours (default 24).
  • A datetime marker field remembers which Date Start was already notified; a matching value short-circuits, so a scheduler that runs every minute produces exactly one notification.
  • When the meeting is rescheduled the old notification row is deleted before the new one is created, so the panel never shows a stale time.
  • Delivery goes through the shared NotificationService: persistent Notification, popup Reminder, WebSocket refresh and Web Push — category meeting, which already existed in the push preferences, so meeting pushes are distinguishable from call pushes.
  • The scheduled job row is created by the metadata entry (isDefault) on install; on an existing install create it once from Admin → Scheduled Jobs or the API.
If you change it
  • Clear the cache after editing any of the metadata files.
  • The marker column is a plain datetime on the meeting table; removing the field means dropping the column and the marker comparisons together.
  • reminderPastHours in the config widens or narrows the catch-up window for both the call and the meeting reminder.
  • A third copy of this pattern (Task reminders) would mean three near-identical jobs — at that point extract a shared base job.

Meetings now carry their product exactly the way calls do. The Meetings list has its own Product Services column, sitting between Parent and Status, so the product a meeting is about can be read straight from the list — and the field is required, so no meeting is ever filed against nothing at all.
